OpenApe Reports: client-authored documents, categories and secure uploads

Clients choose layout, language, content and category. Reports stores multiple publications, provides private access and history, and safely displays uploaded documents.

Purpose and scope

Reports is a general publishing service. The IURIO PR monitor is one client: it produces formatted German technical explanations and sends Telegram notifications linking to the exact publication. Its language, sections and design belong to the client. Other clients can publish completely different documents.

Owner requirements: allow multiple reports, including several on the same day; let clients control categories; prevent uploaded content from executing JavaScript or injecting into the application. Categories organize documents without prescribing a schema, language or renderer.

Use the working host report.openape.ai; reports.openape.ai did not resolve during discovery. Preserve existing test and morning briefing contracts. This work does not migrate the Plans service or its workflow.

Categories and responsibilities

Client

Supplies title, static HTML/CSS document, optional language, category and series association. Generates domain-specific content, presentation and notification text.

Reports

Validates and isolates uploads, stores publications and receipts, enforces access, and provides collection navigation, category filters and immutable links. It does not translate or generate report content.

Add one optional client-supplied category per report initially. Briefings, Test Runs and Plans are examples, not an enum. A new category becomes available after an authorized publication without administrator setup or a server release. Missing categories appear as Uncategorized. Validate bounded plain text, trim whitespace and normalize Unicode consistently while preserving client display spelling. Use stable internal keys for filters, never unchecked labels as HTML or paths.

Scope category discovery and counts to accessible reports. Categories grant no permissions and cannot expand a publisher's scope. Provide All reports and category-filtered views. API and CLI accept the category. Existing adapters map legacy briefings to Briefings and test runs to Test Runs without changing their bodies. Category groups documents across series; a series groups related editions. Multiple labels, category management and moving the Plans lifecycle are outside this initial change.

Milestone 2 — Secure client-authored rendering

Support static HTML and CSS using a maintained parser-based server sanitizer, reusing a suitable existing dependency or justifying a new one. Do not implement a regex sanitizer. Enforce safe elements, attributes and URLs, including malformed input and namespaces. Reject executable uploads and unsupported active formats; exclude scripts, event handlers, executable URL schemes, active embeds, forms, base overrides and refresh directives. Do not reintroduce unsafe HTML after sanitization.

Render documents in an iframe without script or same-origin privileges, separate from the trusted app shell. Set restrictive HTTP response CSP including sandbox on the document response itself so direct navigation cannot bypass isolation. Block unwanted network loads, forms and navigation. Permit ordinary static responsive CSS inside the document, but prevent parent styling and remote fetching through imports, fonts, images or CSS URLs. Only explicitly supported authenticated assets may load; do not fetch arbitrary external URLs server-side.

Use correct MIME types, nosniff and private cache headers. Authenticate every content and asset route, including previews and history. Never expose an executable raw-HTML route at the app origin. If original downloads are exposed, use authenticated attachments and equivalent isolation headers. Treat titles, categories and filenames as untrusted text. Preserve legacy rendering contracts while auditing shared boundaries touched by the change.

Acceptance: established browser suites cover scripts, event handlers, encoded javascript URLs, malformed/mutation XSS, active SVG, DOM clobbering, metadata injection, CSS leakage and unexpected network requests. Verify no attacker execution or parent DOM/style change across saved, preview, history and direct-document routes. Two benign documents with different languages and layouts retain their appearance. Inspect desktop/mobile screenshots, anonymous denial and existing layouts. Retain security regression tests because they protect the upload trust boundary.

References: OWASP XSS prevention, MDN HTTP CSP sandbox, OWASP DOM clobbering prevention. Sanitization, isolation and response policy provide complementary safeguards; document limits and maintain dependencies.
