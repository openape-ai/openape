## Purpose and scope

Build a reusable directed acyclic workflow graph within the existing Electron/SQLite Pods application. Workflows are first-class sidebar entries beside groups, with their own name, nodes, dependency edges, schedule, pause state and history. Each node references an existing Pod; connecting it does not alter its script, settings, resources, lifecycle, existing schedule or group. A Pod can be referenced by multiple workflows, but appears at most once within one workflow in v1. Support multiple roots, fan-out and fan-in: all roots are eligible at workflow start; every other node becomes eligible only after ALL incoming predecessors succeed in that same workflow run. Eligible distinct Pods run concurrently within the existing global limit. Reject cycles, self-edges, duplicate edges/nodes, missing references and foreign-owner Pods at the worker boundary. Arbitrary conditions, OR-joins, loops and cross-device execution remain outside v1.

The workflow is an orchestration layer around existing Pods. A completion-only dependency works with unchanged existing scripts and requires no new script API. Typed output handoff is an optional workflow node integration. Mail filtering needs a separately verified batch-aware integration; merely drawing an edge must never be represented as proof that an opaque script cannot read outside the filtered batch.

The mail pilot uses the explicitly selected Microsoft account `phofmann@delta-mind.at`, its Inbox and an explicitly resolved Archive folder in the same mailbox. It never deletes mail, sends mail, creates forwarding rules, marks mail read or alters the retired automation. Exact account, source/destination folder IDs, rules, protected partners, Pod order and Telegram destination must be reviewed together before live use.

## Execution contract

### Definition, identity and locking

Store revisioned workflow definitions, Pod references, dependency edges and workflow-owned schedules in SQLite. Extend the existing scheduler/intake and clock evaluation to accept a workflow target rather than treating a root Pod's schedule as the workflow schedule. Persist unique workflow trigger identity, workflow runs and node attempts linked to existing Pod runs. Enforce one nonterminal run per workflow with a database uniqueness constraint. Different ready nodes may execute in parallel; the existing global process-slot limit still applies, and the same Pod never executes concurrently with itself.

At admission, reserve the workflow's distinct Pod set atomically in a stable order. A conflicting standalone run, terminal or another workflow produces a visible waiting reason without holding a partial set of reservations. This prevents deadlocks between workflows sharing Pods and prevents Pod checkpoints from changing underneath a blocked workflow. Reserve all members for the run, but consume process slots only for executing nodes. Persist these reservations across failure/interruption until reconciliation and explicit completion/cancellation. Standalone triggers and other workflows remain independent and queue behind the reservation; they do not become workflow triggers. The Pod keeps its existing persistent state, read after reservation; do not silently clone/reset it for each workflow. The UI discloses shared state when a Pod is reused across workflows.

Pin definition revision, graph nodes/edges, validated script hashes, owner/account bindings, resource epochs, rule/protection revision and destination identity at admission. Reject revision races before execution. Recheck current authority before every external action and node transition. A revoked grant or disconnected account blocks further work. Permission/rule changes never silently reinterpret an active batch. Newly added protections take immediate precedence before the next move; removed protections or broader archive rules require a new reviewed revision. Graph edits create a new draft revision and never rewrite an active run. An explicit cancellation can release its reservations only after all ambiguous effects are resolved and running domains stopped.

All run entry points enforce reservation and trigger scope: Schedule, Run now, Script validation/run actions, master/chat actions, recovery and direct dispatcher admission. **Run workflow** presents the graph; **Run Pod** remains a standalone action and does not silently trigger predecessors or the whole workflow. During a workflow reservation, direct Pod/program/terminal execution waits or is refused with the owning workflow identified. Workflow dependency checks cannot be bypassed by submitting a standalone-looking request with workflow authority. Validation remains sandboxed and non-live. Restrict mail-mutating capability to the typed archive executor; generic tool/shell calls must not bypass mailbox, destination, protection or receipt checks for the mail integration. Existing DDISA owner authority remains unchanged; read the protocol before modifying any grant adapter surface.

### Workflow-owned schedules

Support interval, daily, one-time and five-field cron (minute, hour, day of month, month, day of week; no seconds/macros in v1). Pin an IANA timezone, schedule revision and intended slot in each trigger. Reject invalid expressions and show a human-readable summary plus upcoming times before enabling. Reuse existing clock/DST behavior where applicable: repeated local times fire once, missing local times use the next valid occurrence shown by the preview. Define restricted cron day-of-month/day-of-week as conventional OR semantics and show that interpretation. One-time triggers persist their fired identity and never fire twice after restart. Missed occurrences coalesce into one catch-up; backward clock jumps never duplicate acknowledged slots. Resolve a suitable existing cron dependency during implementation before adding one; justify any new dependency and verify parsing/preview/actual execution through the same evaluator. The application still must be running to execute schedules.

### State and transitions

| Condition | Defined behavior |
| --- | --- |
| New trigger | Atomically reserve the workflow and all member Pods; enqueue all root nodes, and show other nodes waiting for their named predecessors. |
| Duplicate manual trigger | Return/show the current workflow run; do not create an implicit second execution. |
| Scheduled triggers while active/blocked | Coalesce to at most one catch-up request. It cannot pass a blocked run. Retain distinct external event identities without silently dropping them. |
| Global slots exhausted | Waiting, with the concurrency-limit reason. Workflow reservation stays held; a waiting workflow consumes no process slot. |
| Successful predecessor | `completed`, acknowledged inputs, confirmed required effects, required outputs and stopped domains satisfy that predecessor edge. A successor is eligible only when ALL incoming edges are satisfied in the same workflow run. An atomic readiness claim starts each node at most once even if two predecessors finish together. Fan-out nodes compete fairly for available slots. |
| `completedWithGaps`, failure, cancellation, missing required output | Block descendants and expose the failed ancestor. Already running independent branches may finish; independent branches may continue if their own prerequisites succeeded. The workflow remains blocked and cannot complete or admit another run. Authority/storage failures pause dispatch globally, not merely one branch. No automatic retry of failed nodes. |
| Workflow paused | No new automatic run or node dispatch. Already executing nodes may reach safe boundaries; no further node starts until explicit resume. |
| Member Pod paused | Existing Pod pause means its own automatic execution is paused. An explicitly configured workflow can invoke it without editing this setting; workflow pause governs workflow triggers. Show this clearly at workflow review. Archival, missing validation or revoked authority always blocks use. No implicit unpause of the Pod. |
| Manual run of a paused workflow | Explicit Run workflow executes the reviewed graph once without enabling its schedule. It lists Pod availability and existing independent schedules. Archived members always block. |
| Pause during a move/send | Stop starting further effects after the in-flight request settles; checkpoint and hold. An uncertain response needs reconciliation. Resume requires an explicit action. |
| Retry | Resume the same workflow run, graph and batch with new attempts for selected unfinished nodes only after their prerequisites hold. Retain completed sibling branches and receipts. A join cannot start until every predecessor succeeds. Changed code/authority requires review before continuation. |
| Worker/app restart or forced termination | Fence old native processes, inspect execution domains, turn dispatched intents into unknown and show recovery required. Never restart an interrupted step or send on startup. A durably completed predecessor with no interrupted work can unlock its successor after revalidation and pause checks; incomplete work requires explicit recovery. |
| App closed or asleep | Use existing local scheduling and missed-slot coalescing. No server-side/always-on promise. |
| Storage full, lost authority, partial enumeration | Block before new effects, retain all existing receipts and the unadvanced input boundary. |
| Whole-workflow completion | Every node must be completed and all required effects settled. A failed branch cannot be hidden by a successful leaf. Release all reservations atomically only at a valid terminal boundary. |

### Generic handoff

Completion-only dependencies require no Pod/script changes: the executor records an immutable completion receipt from existing run state and acknowledged inputs. Optional typed data handoff is configured per workflow node/edge; compatible scripts or trusted invocation adapters can expose versioned output. Multiple predecessor outputs remain keyed by source node and are never implicitly merged or overwritten. Downstream nodes receive only explicitly bound outputs and allowed source references. They cannot read arbitrary Pod checkpoints, credentials or blobs. Validate schema/version and source ownership; register large result blobs with backup/retention.

For the mail integration, prototype an invocation adapter at the existing trusted program broker: the unchanged successor's supported `mail list/read` calls must be constrained to the sealed retained batch, with out-of-batch reads rejected and reply shape preserved. All alternative read paths must respect the same scope. At recovery, legacy `pendingTelegram` still blocks until reconciled; adding the Pod to a graph cannot magically make its script's recovery logic correct. Prove compatibility of the saved short-report script with the scoped batch and outbox contract in M0/M2. If a mail-specific recipe upgrade is necessary, present it as a separate explicit feature change, never an automatic condition or hidden rewrite when adding a Pod to a workflow. Ordinary workflow graph composition must work without that upgrade.

For the mail template use a `mail-filter-result/v1` handoff: mailbox identity, batch ID, baseline/boundary, frozen candidate identities and versions, per-item disposition, retained source references, confirmed move receipts and archive-report delivery receipt IDs. Seal it only when filtering and its required report are complete. Unknown classification is a successful conservative **retain** decision; unreadable/unclassified input, incomplete enumeration or an unknown move is incomplete work and blocks sealing.

## Mail policy and batch contract

### Conservative owner-reviewed rules

Default action is **retain**. Auto-archive requires a positively matched enabled owner rule and no protection. Initially all archive rules are disabled; pilot approval selects exact senders/list identifiers and examples. Suggested first rules are routine promotional newsletters from named mailing lists and redundant informational digests from named automated senders. An unsubscribe link, bulk header, no-reply address, low model score or domain reputation alone is insufficient.

Protected categories are personal correspondence, invoices/receipts/payment requests, contracts/legal correspondence, security/account notices, deadlines, flagged messages, calendar invitations and anything requesting action. Attachments or truncated/unreadable content that cannot be safely classified cause retention. An explicit category exception must be narrow, separately displayed and owner-approved; it must not remove partner protection.

**Protected communication partners** are a first-class mailbox-scoped list: exact normalized email addresses and optional explicit domains, display label and owner note, persisted revision/history. Match structured From, Sender, Reply-To and visible To/Cc counterparts, excluding the assigned mailbox's own recipient identity; preserve exact-address precedence and do not silently broaden domain/subdomain matches. Do not infer aliases, strip plus tags or use display names as identity. Existing conversation evidence involving a protected partner also retains the message; missing or ambiguous evidence means retain. Partner-matched mail is important for notification and can never become an autonomous archive candidate, regardless of archive rules or AI output. A future per-message human exception requires a current immutable message/version review; v1 offers no bulk override. The empty list is shown explicitly and must be reviewed before pilot approval. No addresses are invented or automatically imported from mail content.

AI may propose a bounded classification/reason and summarize retained messages, with tools disabled. Email subjects, bodies, attachments, headers and model output remain untrusted data. Parse constrained output; policy and the trusted executor determine eligibility. Mail cannot edit rules, destinations, dependencies, capabilities or partner lists. Test prompt injections containing forged approvals and fake tool calls. A malformed classification retains the item or blocks an unfinished analysis; it never grants a move.

### First run and fixed batches

No historical inbox processing by default. On the separately approved first live read-only initialization, store a server-backed baseline/delta cursor and a visible start boundary; inventory is metadata-only and causes zero moves or sends. Explicit backlog processing requires a separately reviewed date window and count. New arrivals during baseline enumeration must remain in the following delta; do not advance a wall-clock timestamp in a way that loses them.

Enumerate the next bounded mailbox delta/inbox window into durable batch candidates before any move. Follow provider pagination to the declared batch boundary, store continuation state and deduplicate by mailbox + immutable identity. The successor processes only the sealed batch's retained IDs, never a fresh inbox listing. New arrivals, including arrivals during filtering or notification, go through filtering in the next batch. Late provider visibility must be captured by subsequent delta state, not excluded by a local received-time cutoff. Initial proposed limits: 100 candidate messages per batch, 20 analysis items per resumable work unit, at most 20 archive attempts per pilot run. Reaching a bound retains continuation and leaves the step unfinished; it cannot return a false successful terminal result. The next explicit continuation uses the same workflow reservation.

Before summarization, verify retained items still belong to the batch and remain in Inbox. Owner-moved/deleted mail is skipped with an explicit disposition. Materially changed mail returns to filtering or blocks; never summarize newly changed content under stale filter approval. Protected and uncertain-but-readable retained mail is included in the important-mail summary, with the uncertainty clearly labeled. An empty remainder produces no important-mail Telegram notification.

## Mail effects and Telegram delivery

### Narrow transport prerequisite

Extend the installed CLI's supported machine-readable transport in its own repository rather than revive the deprecated bundled reader or expose Microsoft tokens to scripts. Resolve that repository's current instructions, source identity, hosting and tests before modifying it. Required transport evidence: account identity on every response; stable/immutable message identity, current folder and version; resumable pagination/delta; structured move result including resulting ID/folder; typed known-rejected versus uncertain outcomes; no blind retries for move POSTs; restricted same-mailbox Inbox-to-Archive operations. Keep it explicitly assigned via the current program/credential broker and verified executable hashes. Unsupported versions block with an upgrade/readiness message.

Microsoft documents `Prefer: IdType="ImmutableId"` per request and identity stability for moves within the same mailbox; a separate archive mailbox is excluded. The move API returns a new message resource with `201`. Store both immutable identity and old/new provider IDs; RFC Message-ID is corroborating evidence only and is not assumed unique. See [immutable identifiers](https://learn.microsoft.com/en-us/graph/outlook-immutable-id) and [move API](https://learn.microsoft.com/en-us/graph/api/message-move?view=graph-rest-1.0).

Re-read identity, source folder, relevant flags and version immediately before moving; preserve owner changes and skip stale candidates. Use the folder-scoped move endpoint so a message already removed from Inbox is not fetched from another folder and moved back. Verify postconditions and never compensate by moving a message back automatically. The published move contract does not establish atomic If-Match semantics. M0 must determine a supported concurrency guarantee; a pre-read alone must not be described as atomic. If required version protection cannot be established, expose that limitation and keep autonomous archival unavailable for those cases rather than silently weaken the contract. Synthetic tests prove local handling, not an undocumented Graph guarantee. Any live-provider validation remains separately authorized.

### Per-message evidence and recovery

Use the existing `EffectLedger` for durable intents/receipts, extended with typed move reconciliation and an append-only attempt/audit trail. Persist the approved decision before dispatch: workflow/batch/step, account, immutable identity, before-ID/version/folder, sender, subject, rule/protection revision and reason, destination, effect key and timestamp. Store returned ID/folder/version, provider receipt and outcome immediately after dispatch. Effect identity is based on the logical batch/item/action, never the retry's Pod run ID.

Item outcomes are retained, protected, excluded by owner action, confirmed moved, known failure or unknown. A timeout/process loss after dispatch is unknown even if the CLI exits nonzero. Reconciliation reads current provider state without mutation. Finding a message in Archive without an attributable receipt is evidence of location, not proof that Pods moved it; distinguish owner/external moves. If attribution remains uncertain, require owner review and do not label it as a successful Pods archive. No sender/subject fuzzy match may authorize another move. Confirmed successes survive partial failure; stop further moves on a failed/unknown outcome and block the successor. Retry only unfinished effects proven not applied. Resolved exclusions need an explicit reason and cannot silently turn failure into success.

### Report outbox

Persist report content before sending, including deterministic part boundaries, logical effect key, exact destination identity, content hash and per-part status. Resolve the Telegram token only within the trusted delivery path; keep it out of logs, handoffs and SQLite request bodies. Bind logical identity to the credential resource/bot and destination, not token bytes, so token rotation cannot accidentally produce a new send.

Every confirmed archived message appears individually with sender, subject, reason and receipt reference; split long reports into stable Telegram-sized parts rather than truncate away items. Failures, exclusions and unknown outcomes have separate sections and counts. Long fields may use explicit excerpts, but every item remains listed and its full local audit record is accessible. A failure report may be delivered while the workflow remains blocked; sending that report does not unblock the successor. Freeze each report revision and only send new recovery information in a separately identified update, without resending acknowledged parts.

Validate Telegram's application result, including destination and message ID, before marking delivered. Persist receipts and item notification markers atomically where local state permits. After a crash between receipt persistence and checkpoint advancement, finish local bookkeeping without sending again. Unknown dispatch outcome blocks automatic resend and requires explicit owner evidence or an explicit duplicate-risk resend decision. Never assume a local idempotency key deduplicates Telegram. The Bot API sendMessage contract returns a Message on success and does not expose a client idempotency key; therefore the design intentionally makes no exactly-once claim across an ambiguous response. See [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage).

The archive step is complete only after all dispositions are settled and every required archive-report part is delivered/reconciled. This intentionally delays important-mail notifications if archival reporting is blocked. The successor uses the same durable outbox pattern and a persistent mailbox/message notification ledger. Confirmed notifications are not forgotten by a rolling seen-ID limit. Retries reuse the saved summary; AI is not rerun to generate a different payload for the same effect.
