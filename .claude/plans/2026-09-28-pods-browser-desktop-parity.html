Pods browser workspace: the desktop interface online

After signing in at pods.openape.ai/workspace, users see the same Workflows, Pods and App settings navigation, visual language and Pod editor as in the current desktop app.

Issue 1404 · Approved by owner on 2026-09-28 · Reference source 961960578a934c89a9aacfdc1c601712052908e4 · Estimated scope: several hours, including regression verification and rollout.

Approved scope: Visual and navigation parity with the desktop. Keep the existing remote command capabilities. Workflow and device-only actions that the browser cannot execute receive a clear desktop-required state. This implementation does not create a general remote administration channel.

Purpose and boundaries

  • One set of presentation components serves desktop and browser. Future visual changes must reach both.
  • Workflows is the initial signed-in destination, as on desktop. Workflows and their Pod links are visible from the selected registered runtime; multiple runtimes are explicitly identified.
  • Preserve all currently supported browser operations, including Pod editing, variables, schedules, scripts, run history and the reviewed archive/delete flow.
  • Workflow mutations, local account credentials, MCP grants, native file selection, backups and resource assignment remain desktop-only where the existing remote API does not support them. Show their purpose and desktop-required state in the same sections. Never show fabricated connected states.
  • Retain the public welcome page, login discovery at the correct IdP, callback handling and logout. No redesign of the landing page or DDISA protocol changes.
  • No real workflow runs, Pod deletion, permission changes or messages are required for acceptance.

  • apps/openape-pods/src/renderer/central/DesktopWorkspace.vue owns the desktop frame, Workflows and App settings and embeds CentralWorkspace for Pods.

  • apps/openape-pods/src/renderer/App.vue, PodDescription.vue, PodScript.vue, PodValues.vue, PodResources.vue, PodSettings.vue, PodRuns.vue, WorkflowPanel.vue and AppSettings.vue supply the reference presentation. Several directly call window.pods and need explicit data/action adapters before browser reuse.
  • apps/openape-pods/src/renderer/central/CentralWorkspace.vue has separate remote editor markup and CSS. central/client.ts already separates browser HTTP from desktop IPC.
  • apps/openape-pods/src/contracts/central.ts restricts remote command channels and actions. Workflow archive tables are replicated, but the browser client currently has no workflow view.
  • apps/openape-pods-relay/server/utils/workspace-store.ts, workspace.ts and server/api/workspace/v1/ enforce session owner scope, revisions, online leases and command receipts. Extend bounded reads, not raw archive exposure.

Milestone 1 — Shared workspace shell and destinations

  1. Factor the desktop frame into shared browser-compatible composition, preserving desktop appearance. Make native titlebar decoration explicit.
  2. Load the production desktop styles for the authenticated workspace; prevent generic desktop CSS from changing the public welcome page.
  3. Use the same navigation and account/status presentation in browser and desktop. Browser session and runtime data come through explicit adapters, without a window.pods shim.
  4. Add an owner-scoped, bounded read projection for workflow definitions, membership and run summaries from committed runtime data. Reuse existing parsing and reject invalid records. Empty and unavailable states must be distinct.
  5. Render the existing workflow presentation with explicit read-only capabilities where remote commands are unsupported. Keep Pod links and runtime selection functional.

Acceptance: Login lands on Workflows; sidebar navigation, collapse and current/archive Pods work. Account identity comes from the real session. Expired sessions return to the existing login. Cross-owner workflow reads fail. The desktop frame remains visually unchanged.

Rollback: Revert the shared-shell/read-projection commit. Reads are additive and require no data migration.

Milestone 2 — Shared Pod and settings presentation

  1. Extract reusable views from the existing desktop Pod components. Keep state and transport in adapters; do not copy six screens or introduce a universal service framework.
  2. Bind the browser to existing CentralClient reads and commands, including operation completion and refreshed revision handling. Preserve independent runtime/Pod editor buffers.
  3. Use the same inventory, headings, tab labels, highlighted script editor, variables, permission cards, schedule forms and history presentation. Preserve unsaved edit protection when navigating across tabs, destinations or runtimes.
  4. Reuse the App settings layout. Browser language and account/sign-out controls work; native account, MCP, local resource and backup actions clearly require the desktop. Do not fetch or display secret values.
  5. Remove superseded standalone browser visual rules after all destinations use shared components.

Acceptance: Matching fixtures show equivalent desktop/browser geometry, typography and colors on all six Pod tabs and settings. Supported browser actions still succeed. Offline and stale revisions retain drafts and explain unavailable actions. No browser path calls native-only APIs.

Rollback: Revert this presentation commit while retaining the previously verified shell. No runtime state or stored data transformation is introduced.
