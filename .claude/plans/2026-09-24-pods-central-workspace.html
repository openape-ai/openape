Pods: one central workspace for browser and desktop

Store Pod working data centrally and let the browser and desktop display and edit the same state. Keep execution on the currently assigned Mac. Only online Pods can be opened, edited or controlled.

Purpose and scope

After DDISA sign-in at pods.openape.ai, the owner sees the familiar Pods workspace, their groups and Pods, online status and, for online Pods, configuration and recent runs. Browser, desktop and connected Codex operate on the same versioned data. A successful save means the server committed it. The Mac continues to execute the existing scripts and assigned applications and publishes actual results.

  • Include Pod identity references, groups, descriptions, scripts and versions, ordinary variables, schedules, resource assignment metadata, run history, checkpoints, knowledge and managed workspace artifacts in the central data model. Preserve existing IDs and history.
  • Keep execution secrets, native login state, agent private keys, local process handles, installed programs and owner-assigned external directories on the existing Mac. Store references and readiness metadata centrally. Never upload the entire profile, HOME or Keychain.
  • Maintain current connected-Codex administration and grant enforcement. Current main removed embedded chat through PR 113; do not restore that chat or invent a browser-hosted Codex session. Preserve legacy Pod conversation records as historical data, without copying Codex's own conversation storage.
  • Exclude moving Pods between computers, destination prerequisites, installation management, cloud execution, new mobile features and offline editing or command queues.

Approved architecture decisions

  1. One authoritative store. Add the workspace service and web entry to the existing Pods service codebase, retaining the provider as a separate authority. Use a dedicated workspace SQLite store with immutable artifact BLOBs; do not turn the relay's expiring envelope buffer into the Pod database. Reuse repository database and auth dependencies where suitable.
  2. Versioned commands. Both UI clients and Codex submit typed commands carrying expected revisions and stable operation IDs. The server checks ownership and online availability and commits each accepted change transactionally. Stale edits return a conflict; a retry reuses the operation ID. Execution commands distinguish accepted, started and finished receipts.
  3. Central reads, local execution. The Mac fetches the exact committed script/configuration version for a run. Retain only the local runtime material and bounded journal needed for crash recovery and in-flight effects. Local journals do not become a second editable source of truth. Results and checkpoints commit under actual run IDs.
  4. Explicit liveness. The current Mac reports per-Pod readiness every 10 seconds; an acknowledgement older than 30 seconds makes that Pod offline. A connected process alone is insufficient when the worker cannot serve that Pod. The server checks liveness on detail reads and mutations, not merely in the UI. Reconnect requires reconciliation before online status returns.
  5. Updates without full polling. Start with authenticated cursor-based long-polling, up to 25 seconds per request, backed by a monotonic change sequence. Commit data and its change marker together. Clients refresh affected views; cursor expiry triggers an authorized snapshot. Reuse the runtime connection where appropriate. WebSockets can replace the notification transport later without changing persistence.
  6. Safe disconnection. While disconnected, stop new schedule intake and reject new user commands. An already-running operation may reach a safe local boundary; record its actual outcome durably and reconcile before further work. Do not replay uncertain external effects or mark a timed-out request successful. Existing permission and cancellation boundaries remain intact.
  7. One presentation model. Introduce a typed workspace client at the renderer boundary, with browser and Electron implementations using the central API for shared data. Reuse the existing Vue components and styling. Native-only operations such as opening Terminal.app remain explicit desktop actions. No browser endpoint may accept unrestricted local executable or file paths.
  8. Owner authorization. Web sign-in uses the owner's existing DDISA identity through the SP flow. Bind all central rows and artifact access to verified owner issuer/subject. Runtime credentials are narrowly scoped to the existing assignment. Same-origin mutation protection, bounded inputs and private/no-store content apply. Being the Pod agent IdP does not grant the workspace service the owner's execution authority.
