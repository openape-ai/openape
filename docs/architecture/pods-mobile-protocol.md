# Pods mobile protocol 1.0

Status: implementation draft for [issue 1362](https://repos.openape.ai/patrick/monorepo/issues/1362). The relay and native client have not been deployed or accepted end to end. The approved [living plan](../../.claude/plans/2026-09-20-pods-native-mobile.md) owns milestones, acceptance and release gates.

## Boundaries

`@openape/pods-protocol` defines the application transport; it does not extend DDISA. Swift models live in `apps/openape-pods-ios/Sources/PodsCore`. The contract is JSON over HTTPS and an outbound desktop WSS connection. There is no desktop listener. The existing agent provider and grant broker at pods.openape.ai remain separate from this new relay process. Existing DDISA authorization, agent provisioning and authoritative grant consumption remain unchanged.

Ownership is the exact tuple `(verified issuer, verified subject)`. As DDISA Core §6.1 specifies, the subject may be an email or an ID. The entered email is a discovery/login hint; it is never substituted for the verified subject. Desktop enrollment passes its account email separately from the saved subject and rejects a returned owner that differs from the selected account binding. A runtime registration has an immutable owner, random UUID, generation UUID and independent P-256 signing/agreement keys. A mobile registration has its own keys and revocation epoch. Neither registration is a Pod identity. The local worker binds every remote Pod to an owner and execution runtime before provisioning. Existing agent keys and grants cannot be reassigned by changing the default desktop account.

Desktop SQLite is authoritative for Pods, configuration, conversations, resource revisions, command outcomes and runs. Relay metadata identifies owners/devices and delivery state; it does not prove execution. Mobile caches contain previously viewed, end-to-end decrypted content and explicitly unsent drafts. Creation or execution requires a currently connected desktop.

## Enrollment and sessions

1. The native client generates two independent P-256 keys and a PKCE verifier locally. `POST /api/mobile/v1/session/begin` supplies device UUID, kind (`mobile` or `runtime`), public keys, S256 challenge and requested email.
2. The returned same-origin browser URL starts normal DNS-discovered DDISA authorization. The relay stores independent state, nonce, PKCE and a browser-secret hash for five minutes. Its browser cookie is HttpOnly, SameSite=Lax and HTTPS-only outside disposable loopback tests.
3. `/mobile-auth/callback` verifies browser binding before consuming state. The IdP token exchange is pinned to public DNS addresses, rejects redirects and bounds response time/size. Assertion verification requires the discovered issuer, this service's audience, nonce, direct human actor, subject and time claims. Delegated/agent logins cannot enroll devices. Pilot enrollment additionally requires the exact owner allowlist.
4. A mobile callback uses the associated HTTPS path `/mobile-auth/return`; the native handoff code expires after 60 seconds and is single-use. Desktop polls its own handoff with PKCE and device proof. Neither client receives the original DDISA assertion.
5. Exchange returns an opaque five-minute access token and a rotating refresh family (30-day absolute lifetime, seven-day idle lifetime). Server persistence contains hashes. Refresh requires a signature over `proofBytes('session-refresh', deviceId, SHA256hex(refreshToken))`. A replay with valid device proof revokes the family. A stolen token without its device key cannot rotate or revoke that family.
6. Authenticated HTTP calls require `X-Pods-Request-Id` (UUID), `X-Pods-Request-At` (UTC timestamp), `X-Pods-Body-Digest` (SHA256 hex of exact request bytes, empty for bodyless requests) and `X-Pods-Proof`. The signed nonce is the compact JSON tuple `[method, pathnameAndQuery, SHA256hex(accessToken), timestamp, bodyDigest]`; the signature covers `proofBytes('api-request', requestId, nonce)`. Requests have 30-second clock tolerance and single-use proof IDs. A network retry uses a new request proof and the original encrypted operation envelope.

`proofBytes` is UTF-8 JSON of `["pods-mobile-proof",1,purpose,id,nonce]` without slash escaping. Proof signatures use P-256 ECDSA/SHA-256, 64-byte IEEE-P1363 form, unpadded base64url. This is an application session proof, not a new DDISA assertion or grant.

## Pairing and runtime connection

The desktop connects to `/api/runtime/v1/connect`. Within five seconds it answers the socket's random challenge with protocol major 1, its access token and a signature of `proofBytes('runtime-connect', peerId, nonce)`. The authentication frame also offers major/minor versions, command/query kinds and content modes. The relay intersects these with its own capabilities; it rejects major mismatch or missing `encrypted-v1`. `/api/mobile/v1/capabilities` advertises service support; runtime inventory carries each live intersection. Mobile checks both, and relay admission/dispatch checks runtime support before forwarding new operations. Unsupported operations return 426 without dropping any revision or authorization field. Tokens never appear in URLs. Only one socket generation is active per runtime; replacing it closes the old socket. Heartbeats run every 15 seconds; 45 seconds without a heartbeat means offline. Session validity and revocation are checked before dispatch and delivery.

The desktop and phone display the first 12 hexadecimal digits, grouped into fours, of SHA256 over this UTF-8 JSON tuple:

`["pods-pairing-v1",issuer,subject,runtimeId,generation,runtimeSigningKey,runtimeAgreementKey,deviceId,deviceEpoch,deviceSigningKey,deviceAgreementKey]`

The owner confirms the exact code on both devices. The desktop persists the mobile public keys locally before informing the relay. The phone pins the desktop public keys/generation. Relay login alone cannot authorize a content recipient or silently replace a pinned key. A changed key/generation requires another explicit pairing. Desktop removal persists a local deny before sending `unpair`; it repeats that removal after reconnect. The relay then removes that pairing and its buffered commands/events. Other runtimes remain paired. Mobile Devices lists same-owner runtimes and other mobile registrations; explicit DELETE revokes the selected registration and all its sessions/pairings. A successful inventory refresh removes cached content for missing or changed runtimes; sign-out removes local content, tokens and keys even if remote revocation is temporarily unavailable.

## Envelopes and encryption

The envelope contains `route`, `contentMode: "encrypted-v1"`, `ephemeralKey`, `nonce`, `ciphertext` and `signature`. No plaintext content mode is implemented. Route fields are protocol name `pods-mobile`, major 1, additive minor, operation UUID, runtime UUID, generation UUID, device UUID, key epoch, owner, direction, kind, kind version 1, issued/expiry timestamps and decimal sequence string. The parser rejects unknown commands/major versions before execution; optional future capabilities must be negotiated before use. Unknown JSON fields are not currently negotiated extensions.

Associated data is the fixed tuple:

`[protocol,major,minor,id,runtimeId,generation,deviceId,keyEpoch,owner.issuer,owner.subject,direction,kind,kindVersion,issuedAt,expiresAt,sequence]`

Use UTF-8 compact JSON, no slash escaping, integer revisions, lowercase UUIDs and UTC timestamps with exactly three fractional digits. Content keys use ephemeral P-256 ECDH with the recipient's static agreement key, HKDF-SHA256 with salt SHA256(associated data), info `OpenApe Pods encrypted-v1 P256 HKDF-SHA256 AES256GCM`, and a 32-byte result. AES-256-GCM uses a random 12-byte nonce and authenticates the associated data. `ciphertext` is ciphertext followed by the 16-byte tag. The separate signature authenticates UTF-8 `OpenApe Pods envelope-v1\0`, associated data, one zero byte, and decoded ephemeral key, nonce and ciphertext, concatenated in that order. Public keys use 65-byte uncompressed X9.63 form. All binary fields are unpadded base64url.

The relay sees identity, device/runtime IDs, timing, routing kinds, sizes and delivery outcomes. It cannot decrypt content or sign owner commands. This construction does not offer forward secrecy after compromise of a long-lived recipient agreement key; key rotation requires explicit pairing. Endpoint compromise, screenshots and authorized provider output remain endpoint concerns. Credentials, private keys, provider caches and arbitrary local files are never part of an inventory projection.

Fixtures in `packages/pods-protocol/fixtures` are deliberately synthetic private keys and cross-language ciphertexts. Both CryptoKit-to-TypeScript and TypeScript-to-CryptoKit opening are tested. They are not deployment keys.

## Commands, receipts and reconnect

Supported command kinds are `pod.create`, `pod.rename`, `pod.pause`, `pod.resume`, `chat.send`, `chat.cancel`, `changes.apply`, `changes.discard`, `setup.respond`, `review.prepare`, `review.decide`, `run.start` and `run.cancel`. Each kind has a strict payload allowlist. `review.prepare` snapshots an installed CLI explicitly offered by the desktop owner. `review.decide` approves or denies that exact five-minute review, checking its revision, Pod revision, resource epoch, catalog hash and executable/descriptor/entry-file hashes. Approval creates empty protected program state and an assignment with no execution grants; it never copies credentials. CLI offers containing environment values or application bundles require desktop interaction. Withdrawal prevents new assignments and does not change existing permissions. Ordinary setup answers cannot contain credential values. Query kinds are `inventory`, `conversation`, `run`, `catalog`, `reviews` and `operation`.

Every mutation except creation supplies the current Pod revision. Conversation actions also supply context revision; saved reviews carry their exact revision. Ordinary setup answers bind the proposal hash and current variable revision (including zero for a new variable). Starting a run requires the current script hash and resource epoch. The owner-bound worker repeats these checks before mutation and uses the same existing coordinator/run dispatcher. Authorization/grant checks occur again during execution. Applying a configuration review does not imply a permission grant.

`POST /api/mobile/v1/operations` returns HTTP 202 and a relay `accepted` receipt only after paired-owner, route, signature, online-runtime, expiry and queue checks. The maximum frame is 64 KiB; there are at most 100 pending envelopes per runtime. Creation/chat/query envelopes expire after at most five minutes; other mutations after one minute. The dispatch lease is 30 seconds. No offline mutation queue automatically executes later.

The relay and worker retain an operation ID plus digest. Identical duplicates retain the original outcome; a changed envelope with the same ID is a conflict. Desktop acceptance, local Pod creation/binding/conversation and the corresponding outbox receipt are transactional. Run reservation and its `started` receipt commit together before launch. These facts do not guarantee exactly-once external effects; existing run recovery remains authoritative.

Responses use the original operation ID and a desktop-signed receipt (`applied`, `started`, `completed`, `failed` or uncertain state). Large responses up to 2 MiB split into at most 86 encrypted `event/snapshot` frames, each carrying a 24 KiB piece of the exact JSON bytes. The encrypted transfer metadata contains operation ID, piece count and SHA256 hex; each piece includes its zero-based index and unpadded base64url content. The final `response/receipt` envelope carries the same receipt and transfer metadata. A client retains parts before acknowledging, verifies the full digest and exact receipt before displaying/applying the result, and rejects contradictory duplicate pieces. Larger results carry `unavailable: content_requires_desktop` with the true operation receipt, without implying execution failed or retrying it.

The desktop persists sealed outgoing envelopes before sending, preserving their ciphertext/ID across reconnects. The relay assigns decimal cursors to authenticated events. The phone persists content/cursor before acknowledging; repeated acknowledgements are idempotent. Events expire after 24 hours or mobile acknowledgement. A replay gap returns `resync_required`; `/api/mobile/v1/sync` supplies a current cursor, and clients refresh desktop snapshots and query original operation receipts. They must not reinterpret `unknown` as failure or automatically resubmit it under a new ID.

## Storage, controls and rollout

The relay uses its own SQLite database with WAL and schema guard. Registration and refresh-family revocation remove sessions, pairings and buffered content. Revocation stops subsequent commands; it does not pretend to cancel an already executing desktop process. Explicit run cancellation follows the existing run lease. Restoring a desktop backup disables remote registration, removes paired devices/outbox, fences incomplete commands and requires registration/pairing again.

Relay spool retention is 24 hours, operation/audit metadata 30 days. Mobile viewed entries and drafts expire individually after seven days, with a 50 MiB protected cache limit and backup exclusion. Mobile keys/tokens use Keychain `WhenUnlockedThisDeviceOnly`. Desktop keys/tokens use Electron safeStorage; existing local data encryption behavior is unchanged.

Runtime flags default disabled/closed. Pilot owner allowlists are exact issuer/subject tuples. Required rollout order is contract/server with old behavior preserved, opt-in desktop registration, native internal pilot, then independently approved wider release. Keep existing provider routes and keys untouched. Do not roll an older desktop binary onto schema 22 without its documented backup/restore path. A transport incident can disable the new routes/flag while local Pods continue to function. Never roll an incompatible relay binary against a newer database.

Acceptance is not implied by this contract: full native creation/provisioning/chat/grant/run/result proof, operational deployment, APNs, TestFlight and App Store gates are tracked in the plan.
